# 更新金鑰備援、輪替與事故處理（v1.1.1）

本次沒有生成、替換或讀取任何正式私鑰；原 `DESKTOPPET_PUBLIC_KEY`／`UPDATE_SIGNING_KEY` 保留。新增功能不代表已替你配置備援金鑰。

## 信任與相容規則

- 日常簽署仍為 ECDSA P-256／SHA-256，`update.sig` 仍是 64-byte IEEE P1363 r||s；manifest schema 仍是 1，ZIP 白名單不變。
- `DESKTOPPET_PUBLIC_KEY` 是既有主要信任錨；新增可選 CMake／GitHub Variable `DESKTOPPET_BACKUP_PUBLIC_KEY`，值同樣為 128 hex 的 X||Y，而且須與主要不同。
- 新客戶端接受目前有效主要或備援金鑰簽署的 manifest。未設定備援時維持單金鑰相容模式。
- 舊單金鑰客戶端只認識舊主要金鑰。因此先用既有主要金鑰簽署、發布含備援公開點的新客戶端；備援公開點的信任來自這個已由既有主要金鑰授權的完整程式更新。
- 日常 CI 不需、也不應持有備援私鑰。備援只供離線簽署政策、撤銷／復原事故；日常誤用備援私鑰會因預設角色驗證而失敗。緊急備援簽署須明確加 `-EmergencyBackupSigning`，CI 預設不啟用。

## 設定

如果你已經有獨立的備援金鑰，在 Repository Variable 設定它的公開點，再以原主要私鑰發布橋接版本。這次不重新生成現有主要金鑰，也不代為產生備援私鑰。若尚無備援，先維持單金鑰模式，另在你控制的離線環境準備備援，不要把不明公開點當成備援。

CMake 新增：

```powershell
cmake -S . -B build -A x64 "-DDESKTOPPET_PUBLIC_KEY=$env:DESKTOPPET_PUBLIC_KEY" "-DDESKTOPPET_BACKUP_PUBLIC_KEY=$env:DESKTOPPET_BACKUP_PUBLIC_KEY"
```

保留原 Owner／Repository 等其他建置設定。簽章演算法、正式私鑰與公開金鑰不會因這個指令自行改變。

## 授權輪替與撤銷

政策 payload 是無 BOM UTF-8 JSON：

```json
{"schema":1,"epoch":1,"primary":"新主要公開點128hex","backup":"目前或新備援公開點128hex","minimumVersion":"1.1.1","revoked":["被撤銷公開點128hex"]}
```

以上只是欄位格式，不是實際可用金鑰。`epoch` 從 1 逐次增加；不能重播、跳號或降低版本下限。主要／備援點不能相同，必須是有效 P256 曲線點。移出有效集合的舊點也自動永久列入撤銷，不能在後續政策復活。

**已有備援後，政策只能由目前可信備援私鑰簽署**，避免日常主要私鑰外洩後擅自新增惡意金鑰或撤銷備援。若目前仍是單金鑰模式，第一次新增備援的政策可由既有主要私鑰授權；陌生新金鑰不能自行授權自己。

離線簽署既有政策檔（不產生金鑰）：

```powershell
pwsh -File tools/Sign-TrustPolicy.ps1 -Payload policy.json -OfflinePrivateKeyPath X:/offline-backup.private.key -Output policy-envelope.json
```

把 envelope 依序追加到公開的 `trust/chain.json` JSON 陣列，從第一筆至最新一筆完整保留。此檔只含公開點、政策原文與簽章，可以提交 Git；私鑰不能提交。不要自行重排 payload 的文字或換行，簽章驗證使用原始 UTF-8 bytes。

Package.ps1 自動讀取存在的 `trust/chain.json`，或接受 `-TrustChain` 路徑。原生測試工具會先從編入的既有信任錨驗證完整授權鏈，再允許簽署。新主要金鑰用於日常簽署時，將既有 `UPDATE_SIGNING_KEY` Secret 更新為你已授權的新主要私鑰，另設定 Variable `UPDATE_SIGNING_PUBLIC_KEY` 為新主要公開點；**不要因此覆寫最初的信任錨變數（包括原本為空的備援錨）**。已用單金鑰政策 bootstrap 備援的安裝，繼續保留最初編譯錨，從完整鏈取得目前有效備援；不要再回填不同的編譯根來改寫鏈的起點。未設定此 Variable 時沿用原主要公開點。

輪替資料放在已簽署 manifest 的可選 `trust` 陣列，不新增 Release Asset，也不改原 `update.sig` 格式。新客戶端先驗證政策的既有授權，才接受新有效金鑰簽署；政策只在新版成功通過啟動健康檢查後提交。

目前最多 32 筆輪替政策。滿額或需要更換編譯信任錨時，須另外安排經既有可信金鑰簽署、人工確認的新基準遷移，不能清空撤銷紀錄假裝沒有歷史。

主要金鑰仍可授權日常可執行檔，因此主要私鑰外洩可能導致惡意程式被簽署。備援保護的是宣告信任政策，不是要求每日雙重簽署，也不能保證已執行惡意程式的電腦安全；事故時應從乾淨環境獨立核對並人工遷移。攻擊者若曾簽署極高版本導致版本下限被抬高，也須人工建立可信新基準，不能以降低防回退檢查解決。

## 本機防回退

`%LOCALAPPDATA%\DesktopPet\update-trust.bin` 使用 Windows DPAPI、綁定目前 Windows 使用者保護。保存已授權鏈與最高成功安裝版本；既有政策前綴不能被改寫／縮短，已撤銷金鑰不再被接受，更新不得低於政策下限或最高已安裝版本。

快取損毀／跨 Windows 使用者無法解密時，更新安全失敗；離線寵物仍可使用，不會悄悄退回信任被撤銷金鑰。請保留可驗證備份或使用人工確認的可信新基準處理。

這是每次安裝的本機保護，不是全球撤銷伺服器。控制同一 Windows 帳號／執行檔的攻擊者可以破壞本機環境；刪除安全資料、重裝舊客戶端或從舊備份回復，無法離線保證知道之後發生的所有撤銷。**不要把刪除 trust.bin 或略過簽章當成修復方式。**

## 備份與電腦遷移

- 主要、備援為不同私鑰，分別加密備份；備援私鑰平日離線，至少兩份受控副本存於不同實體位置。記錄公開點、用途、政策 epoch、最高已發布版本及保管者。
- 限制私鑰檔案 ACL，只允許發布者；移轉使用加密媒介或你信任的安全通道，確認新電腦實際可以簽署測試資料並以既有公開點驗證後，再停用舊工作環境。不要直接重新產生同名金鑰來「修復」遺失。
- GitHub 日常只放主要私鑰 Secret。備援私鑰不要放 CI、聊天、issue、雲端公開資料夾或 Release。
- 公開信任鏈可正常備份／遷移；DPAPI 密文不能直接搬到另一個帳號當成有效狀態。新電腦使用目前可信版本及完整公開簽署鏈，另核對已知最高版本與公開點。不要從待驗證更新包中取得並盲目信任一把新根金鑰。

## 遺失與外洩

| 情境 | 處理 |
|---|---|
| 工作電腦遺失，但有主要私鑰加密備份 | 在新環境還原同一把主要私鑰，核對公開點；不用更換客戶端信任錨 |
| 主要私鑰全失、備援仍安全 | 離線由既有備援授權新主要與版本下限；必要時以備援簽署緊急更新；舊單金鑰客戶端需人工遷移 |
| 主要私鑰疑似外洩 | 停用日常發布 Secret／憑證存取，離線用備援授權替換並撤銷舊主要；同步公告已知正確公開點與版本，安排人工遷移舊客戶端 |
| 備援遺失／疑似外洩、主要仍安全 | 無法把一份由不明新備援簽的政策直接當成合法替代；若可取得可信離線副本，先輪替備援；否則以現存主要簽署、經人工及獨立通道核對的新客戶端基準遷移，保留舊信任紀錄供核對 |
| 主要及備援均遺失或均外洩 | 無法僅靠現有線上協定安全自救。必須人工、獨立通道建立新的可信基準；不能用不安全驗證略過恢復自動更新 |

單金鑰舊客戶端無法被遠端程式碼強制賦予它原本不認識的備援，也無法在原主要已失效／外洩時保證自動撤銷。這是信任模型限制；以 [安全手動遷移](MANUAL_MIGRATION.md) 配合已知可信主要或備援公開點處理。

## 驗證範圍

可攜式測試涵蓋未知金鑰拒絕、備援授權、單金鑰 bootstrap、撤銷／復活拒絕、政策重播／改寫／下限回退及最高版本。Windows 額外加入暫時測試金鑰的真實 ECDSA 授權與無效曲線點測試；這些只產生記憶體內測試用金鑰，絕不生成或替換正式金鑰。

Windows DPAPI／ECDSA／交接、PowerShell 簽署／遷移流程尚需 Windows CI／實機執行。本次沒有執行正式輪替、撤銷、發布或 Secret 修改。
